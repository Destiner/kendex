# Phase 5 + W3 plan challenge findings

1. **Critical — W3 device authorization has no settled implementation authority.**  
   **Hits:** §5.4 “Device flow, specified”; §7 W3.  
   Plan specifies a hand-built RFC-8628-shaped protocol while assigning browser sessions to BetterAuth and maintaining separate access/refresh-token tables. It does not define whether BetterAuth or kendex owns client registration, consent, grants, token issuance, scope enforcement, resource/audience binding, or endpoint authentication. Current BetterAuth documentation also exposes device authorization through its OAuth Provider integration in newer releases, so the premise that this must be entirely hand-rolled is version-sensitive. Building the current text would create two partially overlapping auth systems.  
   **Plan amendment:** Before W3, pin an exact BetterAuth version and record an explicit choice: use and threat-model BetterAuth’s supported OAuth device authorization integration, or treat kendex’s implementation as a separate authorization server with a complete RFC 8628/6749 security profile and independent conformance tests. Name the owner of every auth table and route. Prefer the maintained integration if it satisfies required native-client and revocation behavior.

2. **Critical — logout/revocation promise is incompatible with one-hour bearer access tokens.**  
   **Hits:** §5.4 device flow and Auth; §7 W3; Phase 6 submit.  
   The plan says access tokens last one hour, refresh-token revocation propagates before the next poll interval, and `kendex logout` revokes. Revoking only a refresh family does not revoke an already issued bearer access token; it can continue submitting or reading private user data for up to an hour. “Before the next poll interval” describes pending device codes, not access-token enforcement.  
   **Plan amendment:** Choose one enforceable model: opaque access tokens checked against server-side revocation state on every write/private read, or very short-lived audience-bound access tokens plus a denylist/session-version check for immediate logout. Define logout, `/me` revoke, account disable, token-family reuse, and GitHub unlink behavior, then pin tests proving a captured token fails within the stated revocation window.

3. **Critical — private repository non-disclosure is not an explicit transaction invariant.**  
   **Hits:** §5.4 submissions, Privacy, `/me`; §3.6 Submit; §7 W3.  
   `/submit` receives an arbitrary repo string and checks GitHub visibility, but the plan does not say that no marketplace row, job, Blob, rendered excerpt, package metadata, logs, analytics payload, or `/me` result may be created before the public check commits. It also does not define indistinguishable responses for a private repo the caller cannot access versus a nonexistent repo. A failed submission can therefore become a private-repo name/content oracle or leave data for the indexer.  
   **Plan amendment:** Add a fail-closed submission transaction: normalize to GitHub repository ID; authorize caller; verify `visibility == public`; only then persist or dispatch. Before that point retain no repo-derived data beyond security logs with redacted identifiers. Return one non-enumerating error for nonexistent/inaccessible/private repos to unauthorized callers. Add tests for private repos, visibility flips during submit/index, crafted redirects, logs, `/me`, admin queue, Blob, and job dispatch.

4. **High — “ownership” remains contradictory and overclaims GitHub evidence.**  
   **Hits:** §3.6 (“own or belong”); §5.4 route table (`claim` “verified owner”); Auth (“push access, not ownership”); §7 Phase 6 (“you own it”); W3 (“ownership verification”).  
   `permissions.push` proves current push capability, not ownership. Collaborators, teams, GitHub Apps, forks, and organization policy make those different claims. Current wording would force implementation and UI tests to disagree and could let a collaborator “claim” a seeded row as owner.  
   **Plan amendment:** Rename the invariant and every deliverable to **GitHub push authority**. Store `submitted_by` separately from management grants. Define whether any push-capable collaborator can claim/manage/delist, or whether claim requires repository owner/org-owner evidence stronger than push. If stronger evidence is unavailable, remove “owner/ownership” from UI, API, preflight, and tests.

5. **High — GitHub credential lifecycle and BetterAuth account linking are underspecified.**  
   **Hits:** §5.4 schema and Auth; §7 W3; W4 where Google later constrains account identity.  
   Plan shows a simplified BetterAuth `accounts` row with `scopes` but does not decide how provider access tokens are stored, encrypted, refreshed, revoked, or selected when multiple accounts are linked. Nor does it define collision behavior when a later Google login shares an email with an existing GitHub user. Using email as implicit linkage can attach collections or marketplace management to the wrong identity; losing the GitHub token can leave a valid kendex session with stale authority.  
   **Plan amendment:** Adopt BetterAuth’s generated schema/migrations rather than the abbreviated table as normative. Pin account-linking policy: no automatic cross-provider link by email; explicit re-authentication to link/unlink; one identified GitHub account used for repo checks. Encrypt provider tokens at rest with key rotation, request minimum scopes, fail closed on expiry/revocation/SSO denial, and test unlink/relink, duplicate email, deleted provider account, and stale session cases.

6. **High — browser CSRF, origin, cookie, and redirect policy is incomplete.**  
   **Hits:** §5.4 Auth and device approval; `/submit`, `/me`, collection writes; §7 W3/W4.  
   Only `/device` approval explicitly mentions CSRF. Browser submission, claim, delist, re-index, token revoke, account link, and future collection writes are equally state-changing. BetterAuth callback URLs and app-provided browser fallbacks also need an allowlist; otherwise `callbackURL`, forwarded-host confusion, or an untrusted origin can become an open redirect/session or CSRF boundary failure.  
   **Plan amendment:** Add one web-auth contract: exact production `baseURL`; trusted-origin allowlist; secure host-only `HttpOnly`/`SameSite` cookies; proxy/forwarded-host validation; OAuth state/PKCE where supported; same-origin CSRF checks on every cookie-authenticated write; no GET mutation; relative or allowlisted post-auth redirects only. Add hostile `Origin`, `Host`, callback URL, stale state, and cross-site form tests.

7. **High — rate limits are requirements without a deployable design.**  
   **Hits:** §5.4 device flow and Ops; §7 W3.  
   “Per-code, per-IP and per-account” and “every write” do not define shared storage, atomic counters, windows, limits, trusted proxy parsing, IPv6 handling, or responses. Per-instance memory is ineffective across Vercel functions. `/device` code entry, sign-in callbacks, token refresh/reuse, `/submit`, claim, re-index, status polling, `/me`, and token revocation need different abuse budgets. Twenty bits of user-code entropy is safe only if online attempts are globally bounded and codes are invalidated correctly.  
   **Plan amendment:** Select a shared atomic rate-limit store and enumerate route-specific keys/windows/bursts and `Retry-After` behavior. Trust only Vercel’s documented client-IP source, normalize IPv6, bound account and repository fan-out, and make `/device` attempts atomic with lockout/expiry. Tests must span simulated instances and prove IP rotation cannot bypass per-code/per-account limits.

8. **High — Phase 6 depends on status/manage APIs W3 never defines.**  
   **Hits:** §3.6 status rows; §5.4 API table and `/me`; §7 Phase 6/W3.  
   Phase 6 promises status polling and persistence for pending/listed/featured/delisted, but §5.4 defines only submission and claim writes. No authenticated submission-status route, list shape, polling cursor/ETag, ownership rule, or terminal/error state exists. `/me` is a page in the site map, not a versioned API contract usable by app/CLI. Device-token revocation routes are also absent despite `/me` and logout promises.  
   **Plan amendment:** Add versioned app APIs before Phase 6: create submission, get/list caller’s submissions with status/reason and repository ID, revoke token/family, and return connected-account state. Define auth, schemas, caps, ETags/poll interval, not-found privacy, terminal states, and app persistence rules. Add these endpoints explicitly to W3 deliverables and contract tests.

9. **High — “public GitHub repo can be submitted right away” skips required remote authority and freshness checks.**  
   **Hits:** §3.6 use-existing; §5.6 consequences; §7 Phase 5/6.  
   Phase 5 can identify a GitHub-looking remote locally, but cannot prove visibility, push authority, repository ID, default branch, or that the checked local commit is the pushed remote head without W3/GitHub access. “Right away” conflicts with Phase 6’s remote/pushed/public/authenticated preflight. A marketplace-origin folder may also be detached, on a tag, ahead, behind, or have multiple remotes.  
   **Plan amendment:** Make Phase 5 show only local readiness: discovered packages, local check, git state, candidate GitHub remote. Reserve “Ready to submit” for Phase 6 after authenticated GitHub lookup and exact commit reachability verification. Define remote selection, detached HEAD, default branch, multiple remotes, renamed/transferred repo, ahead/behind, and force-push behavior.

10. **High — marketplace-origin import silently loses local edits or republishes the wrong bytes.**  
    **Hits:** §3.6 Import step 1; §7 Phase 5 import tests.  
    “From a marketplace → copied from that marketplace’s files” is wrong when installed bytes were edited locally. Copying immutable source bytes discards edits; copying installed bytes may republish user changes while the UI shows only the upstream licence. Existing provenance/fork state makes this a common, detectable distinction, but no choice or refusal is specified.  
    **Plan amendment:** Snapshot and classify each candidate by provenance and byte comparison at preview: unchanged marketplace item copies immutable commit bytes; edited item shows “your edited copy” versus “original marketplace copy” and requires an explicit choice; unreachable provenance refuses rather than guesses. Apply must revalidate hashes and re-preview on change. Add tests for unchanged, edited, forked, held, source-unreachable, and source-updated-after-preview cases.

11. **High — import licence confirmation is too weak to establish republishing readiness.**  
    **Hits:** §3.6 Import; §5.5 listing licence requirement; §7 Phase 5.  
    A checkbox that “you may republish” does not define unknown/no licence, package licence differing from repository metadata, attribution/notice files, mixed-licence bundles, copied README/assets, or locally edited derivatives. “None yet” in Create also conflicts with submission requiring licence metadata. Confirmation alone must not turn absent permission into valid metadata.  
    **Plan amendment:** Define per-item licence evidence captured in the import preview: detected licence source, unknown/ambiguous state, required attribution/notice files, and whether edits create a derivative. Unknown or absent licence blocks marketplace-origin copying unless user changes source selection or supplies an explicit licence basis; do not synthesize a licence. Copy required notices and retain provenance. Add mixed/unknown/custom/dual-licence and bundle tests. Keep “none yet” valid locally but explicitly submission-blocking.

12. **Medium — “use existing with zero writes” lacks a boundary and later mutations lack stale-preview protection.**  
    **Hits:** §3.6 use-existing; §7 Phase 5.  
    Registering a row under Mine necessarily writes app-owned state, while the test says zero writes. The plan does not state whether zero means repository bytes only, nor whether discovery may write git/cache metadata. Optional “Add kendex.toml” and workflow actions can overwrite files created or changed after discovery.  
    **Plan amendment:** Define zero writes as zero bytes changed inside the selected repository and no git operations that mutate it; app database/cache registration is allowed and tested separately. Each optional write must be its own previewed operation with expected-absence/content hashes, symlink/path containment checks, collision refusal, atomic write, and re-preview on stale state. Never overwrite an existing manifest/workflow; offer a merge preview or refuse.

13. **Medium — scaffold byte stability is untestable as written.**  
    **Hits:** §3.6 Create; §5.5; §7 Phase 5.  
    Scaffold includes user-entered metadata, git-config author, destination-derived names, generated README, workflow versions, licence choice, and potentially platform newline/mode differences. “Byte-stable” does not name fixed inputs, file set, ordering, permissions, timestamps, executable bits, or template version. Dependency/action updates can also change generated bytes unexpectedly.  
    **Plan amendment:** Define a versioned pure scaffold manifest: normalized explicit inputs in, exact relative paths/bytes/modes out; no timestamps, absolute paths, locale, environment, network, or random values. Pin workflow action and kendex-install references by the chosen security policy. Golden-test every licence option and platform path/newline case; test repeated creation from identical normalized inputs produces identical tree hashes.

14. **Medium — three import origins overlap without identity, precedence, or dedup rules.**  
    **Hits:** §3.6 Import; §7 Phase 5.  
    One package can simultaneously be marketplace-managed, adopted/forked, and found on disk. Grouping it under all matching origins permits duplicate names and contradictory source bytes; grouping by one unstated precedence can hide the version the user intended. Existing cross-source collision rules do not decide destination collisions inside a new marketplace.  
    **Plan amendment:** Build one candidate inventory keyed by `(kind, destination name)` with all byte origins and provenance displayed. Define precedence only for presentation, never selection; user chooses when hashes differ. Identical hashes deduplicate with all origins retained. Refuse case-fold/name/path collisions before apply and revalidate the complete destination tree atomically. Add overlap and same-name/different-byte tests across all origin pairs.

15. **Medium — Phase 5 check contract conflicts with shipped Phase 1 gaps.**  
    **Hits:** §3.6 Check; §5.6; §7 Phase 5; tracker deferred item `m10`.  
    Phase 5 says it runs `check --catalog --strict` and calls this the phase-1 check, while the tracker records `check --catalog` as not discovery-aware. A skills.sh-style repo can therefore register successfully through discovery yet fail to check the same package set, or miss findings entirely. `marketplace check` is also listed without saying whether it aliases, wraps, or changes `check --catalog`.  
    **Plan amendment:** Make Phase 5 first close tracker `m10`: authoring check and browse must consume the same `source_config`/discovery result and control-file fail-closed rules. Specify one core check operation and make both CLI spellings and app call it. Pin a test that every package shown by use-existing/import is checked exactly once and findings agree across core, both CLI surfaces, and app.

16. **Medium — token scopes do not cover promised private collection reads, and audience rules are absent.**  
    **Hits:** §5.4 device flow/Auth; §5.8/W4.  
    Device scopes are `submit` and `collections`, but the plan does not split collection read/write, define least privilege, or bind tokens to API audience/client/endpoint beyond a stored endpoint in the local credential. A submit-only token could become accepted for collection mutation if handlers merely require a signed-in bearer. Browser BetterAuth sessions and device bearer tokens also need one explicit authorization mapping.  
    **Plan amendment:** Define server-enforced capabilities (`submission:read`, `submission:write`, `collection:read`, `collection:write`) with least-privilege defaults, audience/resource binding, client ID, issuer, and endpoint/environment validation. Document how BetterAuth browser users map to the same authorization checks. Add cross-scope, cross-environment, wrong-audience, and unlisted-collection access tests before W4.
